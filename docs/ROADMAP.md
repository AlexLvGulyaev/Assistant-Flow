# 🗺️ Assistant Flow — Roadmap

**Статус:** направления развития (не план работ) · **Дата:** 2026-09-15

Документ фиксирует, во что имеет смысл развивать Assistant Flow, если работа над его продуктовой частью возобновится. Это не список задач: ни один пункт ниже не является обязательством, не имеет срока и статуса реализации.

---

## 📍 1. Текущее состояние

Assistant Flow — портфельный актив в сопровождении ([PROJECT_STATE.md](PROJECT_STATE.md)). Подсистемы в строю: мультимодальный ассистент в Telegram (текст, RAG, OCR/Vision, STT/TTS, генерация изображений), управляемая база знаний, Chroma / FAISS / Weaviate, операционная консоль, трассировка и телеметрия, retrieval tuning, RAGAS/evaluation с датасетами, память диалога, demo/admin RBAC.

Технические долги эпохи разработки закрыты (2026-09). Задача следующего этапа — не наращивание количества функций, а уточнение продуктового центра платформы.

---

## 🎯 2. Главный вопрос развития

В текущей документации сосуществуют два близких, но не совпадающих образа AF:

- **платформа для работы с корпоративными знаниями** с полной наблюдаемостью;
- **исследовательская мультимодальная AI-платформа / proof-of-concept**.

Выбор между ними (или их синтез) определяет приоритеты всех остальных направлений.

Рабочая формулировка направления — **Hypothesis, Owner decision required**:

> Assistant Flow развивается от набора мультимодальных AI-возможностей к управляемой платформе для постановки, запуска, оценки и сравнения AI/RAG-экспериментов.

Эта формулировка не является реализованным позиционированием. Текущая система ей соответствует лишь частично: отдельные элементы экспериментального контура есть, целостного сценария — нет. Перед любой продуктовой переработкой требуется отдельное решение владельца.

## 🧪 3. Product / Research directions

### 3.1. Unified experimental workflow — Direction

Сквозной экспериментальный цикл:

```
источник / dataset → retrieval → ответ → evaluation → изменение параметров → повторный прогон → сравнение
```

Компоненты цикла существуют по отдельности (retrieval tuning, evaluation runs, RAGAS, датасеты, трассировка сессий), но не собраны в единый пользовательский сценарий: изменение параметра и повторный прогон не связаны с предыдущим результатом, сравнение — ручное.

### 3.2. RAG/RAGAS как user-facing experiment — Direction

RAGAS/evaluation сейчас — инструмент оператора (раздел «Анализ RAG», отчёты по прогонам). Направление: эксперимент с качеством RAG — первоклассный пользовательский сценарий платформы, а не отчётная функция: запустил прогон, изменил настройку, повторил, сравнил.

### 3.3. Demo sandbox — Direction, Owner decision required

Текущее ограничение: demo-роль read-only; RAGAS/evaluation существует, и demo-пользователь видит результаты, но запуск evaluation-прогонов, импорт датасетов и изменение experimental settings требуют write-прав (403). Публичное демо показывает заметно меньшую часть экспериментальной ценности AF, чем реально есть в платформе.

Направление: **session-isolated experimental sandbox** — демо-пользователь в пределах изолированной временной сессии мог бы:

- запускать evaluation/RAGAS на подготовленном dataset;
- менять ограниченный набор retrieval-параметров;
- сравнивать результаты своих прогонов;
- позднее — работать со своим временным документом/dataset.

Границы: production/global KB остаётся защищённой; административные операции — за admin-токеном; глобальная конфигурация остаётся read-only; sandbox требует собственных TTL/quotas/resource limits. Ничего из этого сейчас не реализовано.

### 3.4. Prompt lifecycle — Direction (architectural debt)

Системные prompt-инструкции захардкожены в Python-коде: `core/orchestrator.py` (prompt enhancement, image-prompt) и `services/rag_query_service.py` (системные инструкции RAG-контура).

Направление развития: внешний SOT промптов, конфигурационный prompt layer, версионирование, activation/rollback, история версий, связь версии промпта с результатом experiment/evaluation; далее — controlled comparison / A-B evaluation.

### 3.5. Experiment entity — Hypothesis

Возможное развитие evaluation layer до явной сущности Experiment, концептуально связывающей: dataset, prompt version, retrieval configuration, model/provider configuration, evaluation metrics, result, сравнение с другим прогоном. Направление описано на уровне продукта/архитектуры; schema/API/UI design — вне этого документа.

### 3.6. Knowledge Base transparency — Direction

Демо-KB должна быть понятна внешнему пользователю: явно показывать, какой корпус используется и из чего состоит, объяснять его назначение, давать примеры вопросов, различать постоянный demo corpus и возможные временные sandbox sources (§3.3).

Цель — убрать ситуацию, когда пользователь задаёт вопрос «по базе знаний», но не понимает, по каким именно знаниям выполняется retrieval.

### 3.7. Роль мультимодальности — Owner decision required

Image Generation, OCR/Vision, STT, TTS, общий AI-диалог не удаляются и не обесцениваются. Открытый вопрос — их будущая роль.

Возможное направление: мультимодальные функции становятся capability modules экспериментальной платформы (участниками экспериментов), а не набором равноправных несвязанных demo-функций. Это направление, а не решение о немедленной переделке UI.

## 🛠️ 4. Platform / Infrastructure directions

Инфраструктурная эволюция; не смешивать с продуктовым целеполаганием (§2–3). Пункты перенесены из [SPEC.md](SPEC.md) § «Вне скоупа» и [PROJECT_STATE.md](PROJECT_STATE.md); все остаются актуальны — ни один не реализован.

| Направление | Обозначение |
|-------------|-------------|
| Semantic / glossary-aware chunking (качество retrieval) | Direction |
| Multi-tenant изоляция | Deferred |
| External IAM / OAuth (например, Keycloak) | Deferred |
| Отдельный контейнер-воркер вместо thread-based execution | Deferred |
| CI/CD | Deferred |
| Автоматические бэкапы и мониторинг инфраструктуры | Deferred |
| S3 / object storage для ассетов | Deferred |

## 🚫 5. Explicitly not committed

ROADMAP описывает направления и гипотезы. Наличие пункта не означает решение о реализации, срок, приоритет или обязательство. Пункты без статуса «реализовано» не находятся в работе; превращение направления в задачу возможно только после решения владельца (§6).

---

## 🧭 6. Owner decisions required

Решения, без которых направления не превращаются в implementation tasks:

1. **Продуктовый центр AF** (§2): экспериментальная платформа vs платформа корпоративных знаний vs их синтез.
2. Принятие или отклонение рабочей формулировки §2 как гипотезы позиционирования.
3. **Demo sandbox** (§3.3): открывать ли write-путь в изолированной сессии — решение о RBAC/permission-дизайне, до любой реализации.
4. **Роль мультимодальности** (§3.7): capability modules vs сохранение текущего равноправного набора.
5. **Prompt lifecycle** (§3.4): старт вынесения SOT промптов (блокирует A-B evaluation и полноценную сущность Experiment).
6. Приоритизация Platform/Infrastructure backlog (§4) относительно продуктовых направлений.
