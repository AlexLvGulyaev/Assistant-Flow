# 2026-09-02 — AF: превью медиа в админ-консоли ломают Basic-диалогом (после демо-стандарта)

## Задание (владелец)

> «AF периодически пароль у меня требует… Пароль просил в режиме аудио и изображений, без этого пароля превью изображений не показывает»
> «Делай, конечно» (вариант 1: авторизованный blob-фетч). Плюс вопрос: «люди с демо-паролем не смогут ничего увидеть?»

## Root cause

Страницы «Изображения»/«Аудио» (`ImagesPage.tsx`, `AudioPage.tsx`) грузят превью через
`<img src="/api/assets/preview?...">` / `<audio><source src=...>`. Такие запросы не несут
Bearer-токен. После внедрения демо-стандарта (02.09) токены настроены → auth-режим авто
`required` → эндпойнт `/api/assets/preview` отвечает 401 с
`WWW-Authenticate: Basic realm="assistant-flow-admin"` (`services/security/auth_middleware.py:55`),
и браузер показывает нативный пароль-диалог; ввод в нём бесполезен (API принимает только
Bearer) → диалог повторяется при каждой загрузке превью. До демо-стандарта режим был
`disabled` — превью грузились свободно, поэтому симптом новый.

## Решение (вариант 1, утверждён владельцем)

Новый хук `useAuthedAssetUrl(ref)`: авторизованный `authAwareFetch` превью-эндпойнта →
blob → `URL.createObjectURL`, revoke при смене/unmount. Подключён вместо
`getAssetPreviewUrl()` в:

- `ImagesPage.tsx`: главный превью + миниатюры-переключатели ассетов;
- `AudioPage.tsx`: входное и выходное аудио.

Медиа остаются под `require_permission(PERM_DOCUMENTS_READ)`.

## Порядок и время (~30–40 мин)

1. Файл задачи — 5 мин.
2. Хук + правки двух страниц — 15 мин.
3. Пересборка admin-ui + деплой — 10 мин.
4. Проверки (curl 401/200, e2e blob) — 10 мин.

## Результаты

### 2. Сопутствующий предсуществующий баг: PII-санитайзер портил asset_ref

Симптом при проверке: превью 404 даже с токеном. Причина: `log_sanitizer.py`
(operational) прогонял все строковые поля через `mask_common_pii` — телефонный
регэксп съедал цифровые прогоны в sha256 → в `processing_logs.details`
`asset_ref` вида `images/69/48/[PHONE]b5b71...png` (26 из 185 записей).

- `services/security/log_sanitizer.py` — `_UNMASKED_KEYS` (asset_ref,
  *_asset_ref, *_sha256, id-ключи): структурные идентификаторы не маскируются;
  юнит-проверка: PII в пользовательских текстах маскируется по-прежнему.
- Ремонт истории: 4 записи починены из соседних полей (`output_images[].path`),
  16 — сопоставлением префикс/суффикс+regex-маски с реальными файлами на диске
  (`/tmp/af_repair_logs.py`, admin-api). Итог: битых asset_ref в БД — 0;
  оставшиеся [PHONE]/[PII] — легитимная маскировка пользовательских текстов.
- Пересборка/рестарт admin-api + assistant-flow; рестарт admin-ui (nginx
  кэширует IP upstream при старте → 502 после пересоздания admin-api).

### Проверки (целевой e2e /tmp/af-media-check.js — 6/6 PASS)

- Демо-вход; превью изображений грузятся как `blob:`; **все** запросы к
  `/api/assets/preview` несут `Authorization`; прямых `<img src=...preview>`
  больше нет; аудио-страница открывается; 0 JS-ошибок.
- curl: без токена → 401; demo-токен → 200 image/png (медиа доступны роли
  demo read-only, так как `/api/assets/preview` охраняется
  `PERM_DOCUMENTS_READ`, входящим в permissions demo).

### Ответ на вопрос владельца про демо-токен

Демо-вход видит всё read-only, включая превью изображений и аудио; любые
мутации (переключение retrieval-бэкенда и т.п.) — 403.

**Статус: DONE** (2026-09-02). Визуальная приёмка — за владельцем
(af-admin.alex-n8n.site → «Изображения»/«Аудио», вход демо-кнопкой или
админ-токеном; пароль-диалог больше не должен появляться).
